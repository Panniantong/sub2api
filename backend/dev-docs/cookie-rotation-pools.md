# 分组 Cookie Host 活跃池与邮箱历史

配置位置：Cookie 库 → 获取配置 / WS → Host 轮换策略。

容量冗余支持 `redundancy_mode=percent`（默认，兼容旧配置）或 `fixed`。比例模式为 `ceil(需求 × (100 + redundancy_percent) / 100)`；固定模式为 `需求 + redundancy_concurrency`。两种数值独立保存、不叠加；固定冗余范围 0–1000000，无请求时仍预留该容量，同时遵守最少 / 最多活跃账号约束。驾驶舱、预览与实际调度使用相同公式。

邮箱冷却或 Host 库读取失败时，可用数量显示“待确认”，不以默认零值证明耗尽。数据库连接池总量应小于 PostgreSQL 可用连接数，并为管理及后台任务留余量。打票运行配置读取失败时禁止退回环境变量重新开启打票；在途打票结果写入前也重新检查开关。

先选择轮换分组，再添加该分组的容量策略。固定需求 70、冗余 50%、每账号并发 35 时，目标容量为 105，选择 3 个账号。不同并发配置按实际容量累加。支持固定目标和实时分配；新策略默认实时分配、最大活跃账户不限制，旧策略保持原固定目标。多选分组共用配置，但按各组请求分别计算。

## 账户池

- 每秒检查，保留现有活跃账号，按账号 ID 和队列游标补位；邮箱重复的账号只计算一次容量。
- 只有 active 状态允许业务调度。preparing 仅允许 Host 验证，standby/waiting/未分配账号不调度。禁用本组策略或后台轮换开关后，该策略范围内账号不调度、不降级。
- 新账号先进入 preparing，绑定有效后转为 active。验证超时、限流、额度阈值或账号失效后让出名额。恢复的账号排在未使用备用账号后面。
- 只有当前绑定不可用、且有效 Cookie 库中全部允许的 Host 都有邮箱冷却记录，才允许降级。仍有未冷却候选、库为空、Cookie 全过期或读取失败均不证明耗尽。
- 分组容量、账号上限和超时均可调整。缩容只撤销新请求资格，在途 HTTP 流保持完成；后续 WS turn 重新校验。
- 同一账号属于多个容量策略分组时，第一个策略拥有该账号；其他原始分组不能绕过策略使用它。未配置策略的轮换分组仍使用原来的全量轮换方式。移除策略即恢复该方式，暂停请使用策略的启用开关。
- PostgreSQL settings 行锁串行提交账户池状态，多实例读取同一成员集。验证再通过规范化邮箱的 PostgreSQL 事务级 advisory lock 互斥；同邮箱不同账号或不同实例不会同时轮换。验证成功后重新检查账号、所属分组和本次入池时间，过期验证结果不能恢复已撤销的名额；业务发送前仍检查账号和池资格。

## 切换时效与边界

- 后台扫描周期为 1 秒；实际发现耗时还包括扫描和数据库操作，不能视为严格的 1 秒切换保证。
- 新补位的 preparing 账户不继承上一轮的 15 秒重试定时器，但仍遵守额度恢复时间。活跃池轮换失败后 1 秒重试；配置的 retry_seconds 控制退出名额后的重新排队等待，两者用途不同。
- 验证成功并保存绑定后立即发布 active 状态，无须再等下一次扫描。就绪容量只统计有效绑定且 Cookie 仍存在、未过期、在 Host 白名单内的账户。
- 活跃池的一轮 Host 尝试总预算为 30 秒，验证还受 preparing 剩余超时限制。该预算约束请求上下文；真实切换耗时受上游验证响应、数据库及取消响应速度影响。
- 验证期间邮箱锁占用一个数据库连接；尚未进行生产多实例压力测试，部署时需要关注连接池余量和实际验证耗时。

页面估算使用账号并发配置，不保证上游实际吞吐量。运行态另外展示 ready_capacity；准备中账号不计入已就绪容量。容量不足时遵循原有排队/503 行为，不将原分组请求自动转入降级组。

## 邮箱持久化

迁移 `241_cookie_email_identity.sql` 新建 `cookie_email_host_cooldowns`，以规范化邮箱和 Host 为复合主键，无账号删除级联。邮箱规范与现有监控一致：凭据 email → extra.email → 含邮箱的账号名称，去首尾空格、转小写。

冷却写入使用 GREATEST，防止并发写入缩短已有冷却。轮换、绑定、调度与后台展示读取邮箱冷却并合并旧账号冷却。邮箱记录不可读时停止该账号调度，不能误判为无冷却。没有邮箱的账号继续使用账号 ID 记录，无法跨删除继承。

验证历史新增 account_email。查询新账号 ID 时同时返回同邮箱历史；页面支持输入完整邮箱查询已删除账号历史，原始 account_id 保留用于追溯。按快速启动要求，部署迁移不做历史回填，也不建立历史表索引；新写入记录按邮箱持久化，旧数据未关联邮箱的部分不保证继承。

## 验证

服务测试覆盖容量计算、补位、恢复排队、额度暂停、缺失 Cookie、配置读取失败、验证后即时就绪、验证期间撤销/禁用/换组/超时、备用与验证态阻断、Host 耗尽判定、邮箱重导入、普通/高级调度器粘性会话和最终发送校验。Repository 测试覆盖事务行锁、邮箱验证锁获取/竞争/异常释放、邮箱独立冷却写入和按新账号查询旧邮箱历史。前端检查包含容量计算、类型检查、ESLint，以及 1440px/390px 浏览器交互和横向溢出检查。

新增迁移已在本地 PGlite（PostgreSQL WASM）执行，验证邮箱规范化、同邮箱取最长冷却、损坏旧时间戳跳过、删除重导入后继承、历史关联和重复执行。上线需要随服务执行新增数据库迁移；本地修改不等于已部署。

扩大 Cookie 测试范围时发现既有 `TestOpenAICodexCookieRequiresTicketResponse` 失败：当前 HEAD 的 captureOpenAICodexCookie 已允许无票响应 Cookie，旧测试仍要求为空。此次未修改该函数或此旧测试；其余相关回归使用 `-skip TestOpenAICodexCookieRequiresTicketResponse` 验证。

## 实时分配（2026-10-09）

需求在用户并发槽位成功后、选择账号前进入 Redis 分组计数，涵盖执行、等待账号和重试，WebSocket 每轮分别计数，空闲连接不计入。请求结束或取消释放，20 秒心跳，进程异常后 60 秒过期。Redis 每秒保存一个峰值，使用配置的 10–3600 秒观察窗口（默认 60 秒）缓冲缩容；每秒后台重算账户池。峰值需求乘以冗余比例后按账号实际并发累加。Redis 不可读时保留上次目标容量，不误判为空闲。

最大账户数 0 表示无策略上限，仍受本组可用账户数量、邮箱去重与 Host 状态约束。空闲时保留最少活跃账户；选中的多个组独立分配，重复分组不能出现在多条规则中。移除规则恢复原全量轮换；暂停规则停止该范围调度，页面提供移除确认说明。

界面测试覆盖多选、暂停开关、移除取消，以及桌面和 390px 移动布局；Redis 测试覆盖去重、组隔离、释放、峰值窗口与崩溃过期。没有新增迁移或历史回填。

## 活跃池驾驶舱（2026-10-09）

容量不足时可使用 `shortage_retry_seconds`（0 沿用普通间隔，非零需为 5 秒至 `retry_seconds`）提前重试准备失败的 waiting 账户。以原重试截止时间扣除间隔差计算，不重置失败时刻；无缺口、自然到期退出、额度恢复时间未到、账户不可调度或 Host 全部冷却时不提前放行。

驾驶舱各账户状态卡片可点击查看明细，每 5 秒刷新。`GET /admin/settings/cookie/dashboard?details_group_id=2` 仅为选中组附带账号、等待原因、恢复时间、准备期限、绑定 Host、当前实例执行中的验证 Host/阶段，以及库内各 Host 的邮箱冷却和白名单状态；不返回 Cookie、凭据或原始验证响应。默认概览不附带账号/Host 明细。当前验证阶段在轮换运行对象内记录，任务结束即移除，不把历史 Host 误当成当前验证。

准备名额与正式容量分离：`preparation_multiplier` 为 1–5 倍（旧策略省略时保持 1 倍，新策略界面默认 2 倍）；`max_preparing_accounts=0` 表示不额外限制准备账户数。先按剩余容量、最少/最大正式账户数估算缺口账户数，再乘准备倍率并应用准备上限。准备失败/超时让出名额，成功发布由数据库池行锁串行检查，目标覆盖后的迟到成功不得写入正式绑定。

自动缩容将已绑定账户标记为 `draining`，记录原绑定截止时间 `drain_until`。绑定有效期间继续接收请求，但不再轮换；到期停止接新请求并退出，不取消已发出的请求。需求回升时允许恢复 `active`，不重置现有绑定期限。手动禁用、额度限制、Host 失效继续优先阻断。准备中且未接入的多余账户可以撤销；在途验证在重试/成功发布前校验当前名额，不允许续上已撤销或退出中的绑定。

`quota_priority` 可选 `used_desc`（已用额度较高优先）、`remaining_desc`（剩余额度充足优先）或空字符串（原顺序）。使用有效 5h/7d 窗口中较高的已用比例，未知数据排后；仅影响 Cookie Host 准备候选顺序，不影响请求选号或已活跃账户的缩容顺序，仍遵守容量、阈值及邮箱冷却检查。

2026-10-10 已撤回 Cookie 活跃池会话历史亲和优化：普通和高级调度器均不再读取最近 3 个历史账号或按历史命中重排，建立及续期主会话绑定时不再写入历史亲和。保留原有主会话粘性、额度优先及实时 Host/额度/并发校验。已有 Redis 历史记录不再被读取，按原 10 分钟 TTL 自然过期，无需清理或回填。

测试覆盖双倍准备、准备上限和超时补位、并发验证抢占正式名额、缩容保留绑定剩余时间、禁止在途轮换续期、需求恢复撤销退出，以及两套调度器的额度优先。发布绑定期间持有池行锁并写账号绑定，需关注数据库连接池余量；未做生产压力测试。

Cookie 页面增加「活跃池驾驶舱」页签，整合采集、轮换、绑定、降级概览与分组容量。分组卡片来自已保存策略，分别展示当前请求、窗口峰值、调度目标与已就绪容量，支持分组搜索和跳转策略管理，每 5 秒刷新。

请求计数使用请求 API Key 的分组 ID，不使用实际执行账号的原始分组。降级组流量单独展示，不影响正常组需求或扩容；HTTP 和 WebSocket 回归测试验证降级请求释放前后正常组当前值及峰值均不增加。已就绪容量仅累加当前仍存在、可调度、入池且 Host 绑定有效并在白名单内的账号；准备中、备用、耗尽、已删除账号不计入。计数不可用显示未知，不伪装为零。
